Attachment Flow
Embedded vs Remote

这份图解只讲一个边界：附件的权威存储在 server，agent 最终拿到的是一个可读的本地路径。 embedded 和 remote 的差异不应该泄漏给 agent，只影响后台如何把这个路径解析出来。

发送方 human 通过 Desktop renderer；agent 通过 silverhand file upload。
权威存储 永远在当前 backend 所属的 blob storage，不在 message snapshot 里。
读取方 agent 通过 silverhand file view 拿本机可读路径。

四个核心对象

Attachment row

数据库真值

attachments 行保存 id、filename、size、content_type、storage、storage_key、 channel_id 和 source_conversation_id。

Blob bytes

文件字节真值

local storage 下落在 backend 的 SILVERHAND_DIR/blobs/...。 remote server 时，这个目录在远端机器上。

Message snapshot

消息里的快照

message 只嵌入 {id, filename, size, content_type}，用于 UI 展示和后续引用。 它不是文件本体，也不是鉴权真值。

Agent local path

agent 可读路径

file view 的输出。embedded 可零拷贝返回 blob path；remote 必须先下载到 attachments-cache。

视角一：human 在 Desktop 里发送附件

Embedded server

Desktop 与 backend 在同一台机器

1
Renderer 上传 multipart POST /api/channels/:id/attachments 或 POST /api/threads/:id/attachments。
2
Backend 解析 owner channel channel 直接归自己；thread 上传时 channel_id 归 parent channel，source_conversation_id 记录 thread。
3
写 attachment row + 本地 blob blob path 由 attachments.storage_key 映射而来，形如 SILVERHAND_DIR/blobs/<storage_key>；不要把 row id 当作文件名契约。
4
发送 message snapshot 消息里只有 id/filename/size/content_type 快照；UI 通过 HTTP 预览。
5
本地 agent file view internal locate 通过 channel guard 后返回 blob local_path；CLI 信任 loopback，直接输出该路径。
Remote server

Desktop 把字节上传到远端 backend

1
Renderer 上传到 remote backend route 与 embedded 相同，只是 backend origin 是远端。
2
远端写 attachment row + 远端 blob 权威 bytes 在 remote server 的 SILVERHAND_DIR/blobs/...，本机没有这份 blob。
3
消息 snapshot 正常广播 本地 Desktop 可以预览，因为 renderer 走 GET /api/attachments/:id 从 remote HTTP 拉字节。
4
本地 agent file view CLI 通过 server URL 判断当前不是 loopback。locate 只用于校验和拿 metadata；返回的 server-local path 会被忽略，随后直接调用 internal download route 拉字节。
5
缓存到 agent 本机 输出 ${SILVERHAND_DIR:-~/.silverhand}/attachments-cache/<conversationId>/<attachmentId>/<filename>。

视角二：agent 通过 CLI 发送附件

Embedded server

agent 原文件和 backend 同机

1
Agent 读取本地文件 silverhand file upload --path /abs/file.png 从 agent 当前机器读字节。
2
Internal upload POST /internal/conversations/:cid/agents/:aid/attachments。agent 不传 channel，backend 用 token 的 conversation 解析。
3
Backend 写本地 blob 即使原文件就在 agent workspace，上传后权威副本仍是 backend blob；原路径不是 attachment 真值。
4
Agent 发送 message silverhand message send --attachment <id> 把 attachment id 嵌进 message snapshot。
5
再次 file view 同 embedded human 路径：locate 后直接返回 backend blob local_path。
Remote server

agent 原文件在本地，权威副本在远端

1
Agent 上传本地文件字节 CLI 读取 --path 指向的本地文件，然后通过 internal route 发到 remote backend。
2
Remote backend 写权威 blob attachment row 和 blob 都在 remote server；本机原文件只是上传来源，不参与后续鉴权或生命周期。
3
Agent 发送 message snapshot 和 human 一样，message 保存附件快照，不保存 bytes。
4
后续 file view 即使是自己刚上传的附件，也按 remote 读取规则：download 到本机 cache 后返回 local path。

为什么 remote cache 不放进 blobs/

blobs/ 是 server authoritative storage

在 embedded 下，本机 server 的 blobs/ 是真值，所以可以直接给 agent。 在 remote 下，本机没有 server authoritative blob；本机副本只是为了 agent 读取的 cache。

  • 放进 blobs/ 会让 cache 看起来像本机 server 真值。
  • 远端删除、GC、channel 清理不会自动同步到本机。
  • 同一个 SILVERHAND_DIR 切回 embedded 时可能误读这些 cache。

attachments-cache/ 是 agent read cache

remote 下载副本放在 ${SILVERHAND_DIR:-~/.silverhand}/attachments-cache/。 这个名字直接表达它不是权威存储，只是 file view 为 agent 准备的本地读路径。

  • 保持 remote-only smoke app 与默认用户数据隔离。
  • 最终输出仍然是 local path，对 agent 使用方式透明。
  • 未来可以单独做 LRU / size cap，不影响 server blob 生命周期。

路由与真值来源

场景 入口 server 负责 agent 最终看到
human 上传 POST /api/channels/:id/attachments
POST /api/threads/:id/attachments		 解析 owner channel，写 attachment row 和 blob。 通过 file view 间接读取，不直接使用 public URL。
agent 上传 POST /internal/conversations/:cid/agents/:aid/attachments 从 agent token 的 conversation 推导 owner channel，写 attachment row 和 blob。 得到 attachment id，后续用 message send --attachment。
renderer 预览 GET /api/attachments/:id 按 route-supplied ACL streaming bytes。 浏览器显示图片或下载文件。
agent 查看 GET /internal/.../attachments/:id/locate
GET /internal/.../attachments/:id/download		 先 locate 做存在性和 channel guard；remote 再 download bytes。 一个本机可读 local path。

排障读法

message 里有 snapshot，不代表 locate 一定成功

snapshot 是消息展示数据；file view 要重新查 attachment row 并做 channel guard。 如果 row 不在当前 server DB、server 版本没有 internal download route、或者跨 channel/thread guard 不通过，都会得到 404。

new CLI + old remote backend 的典型症状

新 CLI 在非 loopback server 下会调用 internal download route；旧 remote server 没有这条 route， 所以表现为 not_found (HTTP 404)。部署含新 route 的 server 后再测，才是有效结果。

channel_id = ACL boundary source_conversation_id = upload origin message snapshot != blob truth remote cache != blobs
