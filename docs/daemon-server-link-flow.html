1. Desktop embedded：D3 two-phase boot 目标链路

关键点：daemon 进程可以先起，但 outbound 不能在 main 写入当前 backend URL 的 config 之前消费旧 config。 因此 desktop 初始 spawn 不传 --host-config；login/claim 后再显式 attach。

2. Connected 后：control plane 和 runtime event plane 分离

embedded V1 不把 runtime events 改走 WS。WS 在这里是 host lifecycle / token rotation / future command 的控制通道； agent spawn、wake、stdout/stderr、runtime status 仍由 daemon IPC 进入 backend 投影。

current V1 invariant

3. Final form：单一 backend codebase + 一套协议；部署形态 embedded / standalone 共存

backend 是一份代码、一套 wire protocol。部署可以是 embedded（inline 进 Electron，loopback 加速）或 standalone（remote fleet，TLS）。 embedded 模式下的 IPC 短路、loopback HTTP、本机 supervisor 都只是 transport 层 adapter， 承载的必须是同一套 outbound frame envelope / auth / error code / ACL 语义——禁止协议 fork。 下面这张图画的是 standalone 部署下 backend 作为 relay 的拓扑：daemon 上来的 runtime events fanout 给 UI，UI 下来的 intent 路由到目标 daemon； embedded 部署下同样的边只是把 transport 换成 Unix socket / 进程内函数调用，frame 形状不变。 agent ↔ daemon 永远是同机 stdio IPC；daemon-placement（local vs sandbox）只是位置 + capability/fs 边界，不是另一种 backend。

future / 终态

4. 正交子问题：同一台 host 上多 daemon installation + capability placement

注意这是「同一台 host 上跑多个 daemon」的问题——比如用户机器上同时跑一个 local daemon 和一个本机 sandbox daemon（受限 fs / PATH / secrets）。 它和 Panel 3 的「daemon-placement = local vs sandbox」是 正交维度：Panel 3 解释「daemon 进哪台机器」，这里解释「同一台机器里如何并存多个 daemon installation」。 两个维度可以叠加：用户机器可以有多个本地 daemon installation；datacenter 也可以有多种 sandbox container 镜像。 sandbox 不是 host_descriptor.kind，是 daemon installation + capability + mount 边界。

共同骨架 / 终态不变量
同一份 backend codebase、同一份 daemon binary、同一份 agent CLI、同一套 HostRuntime intent schema、同一组 host_outbound_attach 失败 reason、 同一条 attach watchdog 新鲜度契约、同一组 BackendInfo local_host_status 5 值（offline | connecting | online | revoked | failed）。 终态原则一句话：same backend, same protocol, multiple deployment adapters——要避免的是 protocol semantic fork， 不是 embedded 部署本身。
