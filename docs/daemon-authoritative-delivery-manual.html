Daemon-Authoritative Message Delivery Manual

本手册定义下一代消息投递架构的责任边界、确认语义和迁移路线。目标是移除 backend 对易失 runtime cache 的生命周期决策依赖，同时保持数据库 inbox、去重、排序和 ack 语义仍由 backend 统一持有。

1. Executive Summary

目标不是把消息持久化责任迁入 daemon，而是把 runtime lifecycle 相关的具体投递动作迁入 daemon。Backend 仍是 durable inbox 的唯一写入者和 ack authority。

Normative

保持不变的责任

Backend 继续拥有 conversation_inbox、delivery claim、排序、去重、in-flight rollback、delivered_at 写入和 message stale/conflict 语义。

迁移的责任

Daemon 成为 runtime lifecycle 和 driver readiness 的权威，决定具体投递动作：start、wake、defer、refuse 或等待 exit/respawn。

Ack 规则

发送到 daemon 不等于 ack。只有 daemon 明确发出 runtime_delivery_consumed 后，backend 才能写 delivered_at。

故障规则

Daemon crash、transport disconnect、runtime refusal、driver not ready 和 timeout 都不得丢消息。未确认 delivery row 必须回到 pending，可由后续事件或用户消息重试。

2. Current Mechanism

当前机制由 backend 先根据本地 cache 选择 start 或 wake，再由 daemon 决定 wake 是否真正写入 runtime。该模型在 cache projection 与 daemon reality 脱节时存在错误路由风险。

2.2 Current Short-Term Fix

The bounded hotfix changes only the dead-end branch. It does not rewrite normal ready wake, first spawn, ready-for-drain replay, or respawn-on-exit.

Bounded Bugfix 
sequenceDiagram
  autonumber
  participant B as Backend
  participant C as RunStateCache
  participant D as Daemon Supervisor
  participant R as Agent Runtime

  B->>D: runtime_start(startup_delivery)
  D-->>B: started=true, startup_delivery_accepted=false
  B->>B: rollback claimed delivery ids to pending
  B->>C: patch temporary wake-routing projection
  B->>D: runtime_wake(delivery ids, text)
  alt daemon handle is ready and driver accepts
    D->>R: write stdin or send ACP prompt
    D-->>B: delivered=true, delivery_ids
    B->>B: mark delivered_at
  else daemon handle is startup_pending, draining, or driver not ready
    D-->>B: delivered=false, reason
    B->>B: row remains pending
  end

3. Target Architecture

The target architecture gives the daemon authority over runtime lifecycle decisions while preserving backend authority over durable message state.

3.1 Command Semantics

The target command is runtime_deliver. It transfers a delivery intent to the daemon, but it does not by itself acknowledge the database row.

Protocol Contract
Disposition / Event
Meaning
Backend action
spawning
Daemon has no live handle and starts a runtime with this batch as startup delivery.
Do not mark delivered. Keep row in-flight until consumed or failed.
admitted
Daemon took the bytes toward stdin or ACP prompt. Runtime-specific consumed proof has not necessarily been observed.
Do not mark delivered. Keep row in-flight until consumed or failed.
deferred
Daemon queued the delivery behind init or a gated-driver safe boundary.
Do not mark delivered. Keep row in-flight; disconnect or ack-timeout rolls it back to pending.
refused
Daemon cannot take custody for a typed reason such as draining, cooldown, invalid metadata, or fatal driver refusal.
Rollback to pending or surface a typed fatal failure. Never ack.
runtime_delivery_consumed
Daemon observed the runtime-specific proof that these delivery ids were consumed.
Mark exactly those delivery ids delivered and clear their in-flight ownership.
runtime_delivery_failed
Daemon accepted custody but later failed before consumed proof.
Rollback to pending when retriable; surface typed fatal failure when not retriable.

3.2 Ack Discipline

The following sequence is the key data-loss prevention rule. A daemon queue is volatile; the database row remains the durable source of truth.

No-Loss Rule 
sequenceDiagram
  autonumber
  participant B as Backend DB owner
  participant D as Daemon queue owner
  participant R as Runtime process

  B->>B: claim pending delivery ids
  B->>D: runtime_deliver(ids, text, metadata, spawn_options)
  D-->>B: spawning / admitted / deferred
  Note over B: No delivered_at write yet.
  D->>D: hold in volatile queue until safe boundary
  D->>R: write stdin / ACP prompt
  alt runtime delivery succeeds
    D-->>B: runtime_delivery_consumed(ids)
    B->>B: mark delivered_at for ids
  else daemon exits before consumed
    D-xB: transport disconnect
    B->>B: rollback in-flight ids to pending
  else runtime refuses
    D-->>B: runtime_delivery_failed(ids, reason)
    B->>B: rollback ids to pending or surface typed failure
  end

4.1 Review Invariants

These invariants should be asserted in code review and covered by tests on the authoritative path.

Checklist
Backend must not mark a delivery row delivered merely because a command was sent to daemon or admitted/deferred into a daemon queue.
Every daemon refusal or transport failure must preserve or restore pending retryability for the affected delivery ids.
Daemon lifecycle state must override backend cache projection when they conflict.
Structured delivery metadata must match delivery ids exactly; daemon should reject mismatches as backend bugs.
Requires-first-message runtimes must retain their consumed-proof gate; initial stdin write alone is not necessarily sufficient for ack.
Cold daemon hydrate must not spawn historical backlog. Recovery should target live runtimes or explicit user-triggered delivery.
Tests must cover ready, startup_pending, draining, not_running, daemon disconnect while queued, driver_refused, and init-gated delivery.

4.3 Open Decisions

These decisions should be resolved before implementation proceeds beyond the bounded hotfix.

Decision Gate
Decision
Recommended resolution
Rationale
Stage 1 shape
Extend idempotent runtime_start responses with the current daemon phase.
Smallest correct step. It removes the cache-heal bridge before the larger command consolidation.
Daemon instance key
Converge all daemon key construction through one shared function before phase stamping.
A single authority identifier is required before backend uses daemon responses to correct projection state.
Ack-timeout value
Treat as an empirical tuning parameter. Do not hardcode a value before measuring legitimate long mid-turn holds.
A timeout that is too short creates duplicate work; a timeout that is too long delays recovery.
Stage 3 scope
Land Stage 1 and Stage 2 first. Move the gated safe-boundary queue only behind a separate crash-safety review gate.
Queue movement is the highest-risk part because it introduces daemon-held volatile custody.
