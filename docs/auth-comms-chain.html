授权 & 通信链路 — 连线图

5 个主体的序列图。每条箭头 = 一次调用，颜色 = 这一跳出示的凭证。①–⑦ 是时间顺序。 虚线 = 本地 IPC / 落盘；实线 = 网络（embedded 下是 loopback，远端是 wss，协议帧相同）。

user session token host token agent token（per spawn） viewer cookie 本地 IPC / 落盘（无网络 token）

为什么三种 token 分开？— 一条 principal 层级链

不是简单"daemon 不是 user"。而是 user → host → agent 三层独立 principal， 各有不同的生命周期 / scope / 信任级别，所以故意用三个 token，不合并。

① 生命周期解耦（最关键）

logout 不该拆掉后台 daemon——机器还注册着（host token 跨 logout 存活）； 反过来注销丢失的笔记本（revoke host）也不该强制各处重新登录。两个生命周期独立，才能各自操作。

② capability 面不同

user session 打 user 级 API；host token 只授权 daemon 传输通道（runtime intent/event），不带 user 全权； agent token 只能动它自己那个 conversation/agent。不让长期后台凭证 = 完整 user 权限。

沙箱 host（future）：host token 从哪来？

不变量：host token 永远由 server 通过 POST /api/hosts/claim-or-create 铸造，而该端点要求 user session bearer—— "注册一台新 host"永远由一个登录用户授权。沙箱 host 仍是被某个 user claim 出来的，不会凭空以自己身份认证。变的只是 token 怎么投送进沙箱（provisioning），不是它从哪来。

今天 · embedded（同机）

desktop main 自己持 user session，自己 claim；daemon 同机，直接把 token 写本机 daemon-config.json。

沙箱 · future（异机，设计已 defer，未实现）

bootstrap-token 交换：模型层已预留 kind = bootstrap vs long_lived （verifyHostToken 拒绝 bootstrap 当长期连接 token）。预期流程：user 给沙箱 provisioning 一个一次性短命 bootstrap token， 沙箱首次连上用它换一个 long_lived host token，bootstrap 随即 consumed——长期密钥不经过 provisioning 管道。

协议完全不变（R1–R4）：沙箱 daemon 说的还是同一套 outbound frame，只有"凭证投送/provisioning"这一层不同。 这正是 D2.0 §5.1 把 secret provisioning 单独 defer 的原因——它独立于协议，不该和传输混在一起。 一句话：user 授权一切 host 的诞生；host 是独立长期 principal；沙箱只改了 token 投送方式，没改"谁有权造 token"和"daemon 说什么协议"。

V1 威胁模型：desktop 在信任边界内，真正要守的是 server 侧。本地凭证统一 0600 明文（去 safeStorage/keychain）； 客户端只承诺「renderer 不可见 + 不进日志/IPC/附件 + 不意外搭便车流出」，加密留给 server 侧的 hash + scope + 即时 revoke + TTL/rotation。 升级触发：backend 真上云 + 多用户 + 不可信本机时，session/host token 一起迁真正的 secret store。
