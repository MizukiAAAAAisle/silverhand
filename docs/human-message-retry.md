# Human message retry identity

The human send body accepts optional `client_message_id`: a canonical UUID v4 (36 characters, hexadecimal case accepted and normalized to lowercase). Generate one UUID per logical send and retain it for retries. Omitting it preserves the old non-idempotent request. Agent send/stale behavior is unchanged.

The authenticated human ID plus this UUID is the unique key across conversations. The request identity compares admitted content bytes, actual conversation ID, the explicit reply-to message coordinate (or main line), and normalized attachment references including their order and labels. Absent and empty attachment lists agree; UUID case and the existing attachment normalization agree. Changing any message-affecting value returns HTTP 409, code `client_message_conflict`. Do not reuse a token for an edited draft. Authentication and current post authority run before reading a prior result, including inside the SQLite write transaction. The UUID is never a read capability.

Both human endpoints (`POST /api/channels/:id/messages` and the existing direct-pair first-send endpoint) pass the identity through the same write unit. Pair initiation retains its existing independent lifecycle: opening a pair precedes sending its first message; a later send refusal does not roll back or erase that pair. No runtime session is allocated by idempotency.

The first commit and a successful retry both return the existing 201 ACK shape. `message.id` and `message.seq` remain server identities; `message.client_message_id` is the correlation key, also on the original WS message event and HTTP message-window/search readback. It is absent on old/tokenless/agent rows. Cache reconciliation must include authenticated sender identity, and ultimately merge by server message ID, regardless of ACK/WS arrival order. A replay returns the persisted message, not another publication. It does not repeat sequence allocation, attachment snapshots, mention copies, inbox writes, notifications, starts, or delivery. Retry ACKs omit attempt diagnostics and old projection sidecars; they are not a replay of potentially stale thread aggregates. Existing HTTP reads remain the recovery authority.

SQLite serializes the send under its existing root write transaction; a unique partial index on `(from_user_id, client_message_id)` is the durable backstop. The normalized request is stored on the same message row and never exposed in a DTO. There is no receipt service, outbox, lease, or expiry coordinator.

The guarantee lasts while the message row and authenticated sender exist. There is no time-based token expiry. Physical message deletion (including conversation cascade deletion) ends it: the token is not a tombstone and must not be used to resurrect a deleted send. If a message alone is physically removed while the target remains writable, a later request with that token can create a new server identity; after target deletion the existing target authorization/not-found gate refuses. This is not perpetual exactly-once delivery. Existing post-commit failures retain their current best-effort behavior; retries do not re-run those effects.

Migration step 92 appends nullable columns and the unique index; existing messages are unchanged and have no correlation key. Use the ordinary migration/backup admission. Deployment correction: Shiki verified the live ECS `/api/server/info` reports Desktop current/minimum epochs 3/3 and outbound protocol 10. A local epoch-2 release tag does not establish that epoch 3 is undeployed. Older epoch-3 servers may lack correlation and retry idempotency while passing the same-epoch admission check; they are not safe peers for clients relying on this contract. An atomic Desktop API epoch/minimum-client/minimum-server bump to 4 is proposed and awaits user confirmation. Until that decision is implemented, matching source builds are required and the admission gap remains. No daemon protocol change, automatic client retry policy, renderer change, packaging or publication is included.
