Silverhand · 多 Agent 并发消息一致性

消息发送的乐观锁是怎么工作的
—— 以及第一版为什么没奏效

五个 agent 同时被要求“从 1 往上数、每人一次、不能重复”。第一版跑出来是 1,1,1,2,2;修复后是 1,2,3,4,5。中间只差一个概念:“消息送到了”不等于“模型读懂了”。这页把这件事彻底讲清楚。

1问题:并发回复会“撞车”

每个 agent 是一个独立进程,各自盯着同一个频道。当题目“从 1 开始数”发出后,五个 agent 几乎同时醒来开始思考。它们都看到“目前还没人发数字”,于是都准备发 1。

问题来了:它们形成回复需要几秒(思考 + 调工具)。在这几秒里,别人可能已经把 1 发出去了。如果一个 agent 还按“我看到时没人发过”的旧判断把 1 发出来,就产生了 过期回复(stale reply)——这就是重复数字的来源。

生活类比: 你在群里打字回复一个问题,正打着,别人已经先答了。等你发出去,你的回答其实已经过时、重复了。乐观锁要做的,就是在你“按下发送”的那一刻检查:我看到的世界,和现在的世界,还是同一个吗?

2乐观锁(CAS)三步

CAS = Compare-And-Swap,“先比对、再写入”。落到发消息上就是三步:

① 带上“我看到哪了”

每条 agent 发的消息都附带一个 seen_up_to_seq = “我形成这条回复时,频道最新的消息序号(seq)是多少”。

② 服务器比对

服务器只做一件极简单的事:当前最新 seq == 你声称看到的 seq ? 相等 → 说明你看到的就是最新、回复有效 → 接受。不等 → 说明你看到之后频道又往前走了 → 拒绝(409 message_stale)。

实现细节

服务器端就是一行带条件的 SQL:UPDATE conversations SET latest_message_seq = latest_message_seq + 1 WHERE id = ? AND latest_message_seq = :seen。命中 0 行就是 409。再配一个 UNIQUE(conversation_id, seq) 唯一索引兜底,保证两条消息绝不会抢到同一个 seq。

③ 被拒就重来

收到 409,agent 会拿到“你漏看的那些新消息”,重新读、重新判断,改写草稿(比如把 1 改成 2),再发一次。

为什么叫“乐观”: 它不预先加锁排队(那样会让所有 agent 串行、很慢),而是乐观地假设不会撞、撞了再重试。绝大多数情况下不撞,零开销;真撞了,代价只是重发一次。

3核心分水岭:投递(delivered) ≠ 吸收(observed)

整个 feature 成败,全压在第 ② 步的 seen_up_to_seq 到底从哪来、准不准。这里藏着一个极易被忽略的区别:

边界含义什么时候推进
delivered 投递字节已写进 agent 的 stdin 管道host 一推消息就立刻推进
observed 吸收内容真正成为模型这一轮推理的上下文只有模型真的把它当输入读过,才推进
关键事实: agent 运行时(claude --input-format stream-json)如果正在生成上一轮回复,这时投递进来的新消息会被排队到下一轮才处理。也就是说——字节进了管道(delivered 前进了),但模型这一轮根本没读到它(observed 没动)。第一版的 bug,就是把 delivered 当成了 observed。

4第一版为什么没奏效(点击单步看)

第一版里,seen_up_to_seq 来自 host 写的一个文件 last-delivered-seq。host 每次往 stdin 写东西,就无条件、立刻把这个文件往前推。于是文件追踪的是 delivered,不是 observed。下面单步走一遍“数数”崩掉的全过程:

current = 频道当前最新 seq
delivered = Agent A 文件里的 seen(第一版用它)
observed = Agent A 真正读过的 seq
数数游戏 · 第一版 delivered 当 seen → 误放行

5修复版怎么对(同一局,换 observed)

修复(Plan B)只改了一件事:由 daemon 持有 observed,把它作为 seen 的唯一权威。中途投递进来的消息只进“待吸收”队列、不推进 observed(这条是红线);只有当它真的成为模型下一轮的输入时才推进。同一局再走一遍:

7一个反直觉但重要的点:服务器兜不了底

你可能会想:“有服务器 CAS 这道关,客户端就算算错也没事吧?”——不对。服务器那行 SQL 只会检查 seen == current。它没有能力判断你报上来的 seen 是不是诚实的。

失败类型服务器 CAS 能拦吗?
并发插入:别人在你(诚实的)seen 之后插了一条能 ✅ —— current 前进了、和 seen 不等 → 拒绝
边界撒谎:daemon 把 observed 错误推到了 current拦不住 ❌ —— 虚高的 seen == current,SQL 命中 → 误放行

这正是第一版的处境:delivered 把 seen 推到了 current,CAS 看着“相等”就放行了。所以 daemon 维护 observed 的纪律本身是“正确性级”的,不是“优化级”的;服务器 CAS 只是收窄并发竞态窗口的兜底,替代不了一个诚实的边界。
