问题 · 01

人还在负责判断，
但已经跟不上
Agent 的速度。

→下一页 · 三个具体痛点
人参与 AI 开发时的三个痛点

带宽 · 知识 · 注意力。

01

带宽跟不上

Agent 一次能读很多文件、跑很多命令；人一次只能认真看一件事。长对话、长 diff、多轮工具输出——很快失去全局感。

02

上下文记不住

Agent 临时读完整个 repo、翻文档、查日志。人不可能记住每个细节。最后 review 很容易变成「看起来差不多」，而不是基于完整证据。

03

注意力会耗尽

长期高质量判断很消耗。Agent 输出越多，人越容易疲劳——review 会从认真检查，变成点头确认。

真实的样子 · Evidence A

面对又长又密的输出，
人很难一眼看完。

这是 Silverhand 自己开发时的真实对话。带宽 / 理解成本 / 知识储备—— 任一环节卡住，人就成了瓶颈。即使勉强跟上，效率也远远赶不上 Agent。

问题 · 02

一个 Agent 容易
沿着错误方向
越走越远。

→下一页 · 它为什么停不下来
为什么单一 Agent 不够

自己写、自己评，
很容易越写越像对的。

一个模型自己写、自己解释、自己判断——它会越写越觉得自己对， 哪怕方向已经偏了。把一个有偏差的方案讲得越来越像对的， 这是它最危险的状态。

这不是它笨，而是没人从另一个角度检查它。 复杂任务里的错误大多不是语法错——是方向错、边界错、设计思路错。 这种错误，只有另一个视角看得见。

解法 · 01

多 Agent 不是
让 AI 多说几遍，
而是让它们分工、互相检查。

→下一页 · 真正起作用的三个条件
让多 Agent 真正起作用

分工清楚 · 视角不同 · 同一份上下文。

01 分工清楚 规划 · 实现 · 评审 · 总结，职责分开，才会真的检查彼此的结论
02 视角不同 A 没注意到的问题，B 可能会问出来
03 同一份上下文 同一份代码、对话、决策——否则只是各说各话
缺任何一项，多 Agent 就会退化成「两个 AI 互相附和」。
Fig. 02
交叉验证 · 互为制衡
真实的样子 · Evidence B

另一个 Agent，
真的能挑出关键问题。

同样是 Silverhand 自己开发时的对话。一个 Agent 给出方案，另一个 Agent 不是点头， 而是提出具体反馈，方向被及时纠回来——这就是「分工 + 互相检查」的实际样子。

解法 · 02

产品要提供的
不是聊天框，
是协作回路。

→下一页 · 项目空间 · 讨论区 · 角色 · 任务
怎么搭这个回路

看得见 · 管得住 · 查得到。

多 Agent 协作真正跑起来，需要的不是「打开多个窗口」， 而是结构化的共享空间。

01 同一个项目空间 / 讨论区 也就是 workspace / channel：多 Agent 看的是同一份历史与文件
02 明确的角色分工 规划者 / 实现者 / 评审者 / 总结者
03 可管理的任务状态 谁负责、做到哪、等谁确认，一眼能看清
04 可验证的结果 回得到文件、命令、测试与历史证据

解法 · 03

人没有退出，
只是不再盯每一步。

→下一页 · Agent 整理证据，人做决定
人的新位置

Agent 整理证据，
人做关键决定。

Agent 之间先在机器速度上完成互相补充、互相质疑、把证据讲清楚， 把问题处理到更清晰的状态，再交给人做关键判断。

人不再做每一步的 reviewer——
而是定方向、看关键节点、做最终决定。
Loop 跑在机器速度上，人只在该介入的地方介入。

边界 · 01

再加一个 AI 帮 review，
和让多个 AI 组队，
不是一回事。

→下一页 · 和「单 AI + 评审插件」的区别
和「单 AI + 一个评审插件」的常见思路相比

一个是加工具，
一个是组团队。

A 插件方案：当成工具调用 主 AI 写完后，让另一个 AI 看一眼。后者只能看到主 AI 传过去的那一段内容，问一次、答一次。
适合「写完后帮我 review 一下 diff」这种轻量场景。
B 协作方案：当成对等队友 多个 AI 看同一份历史 / 文件 / 任务 / 决策。它们可以多轮追问、互相反驳，也可以接力完成任务。
适合长期协作、角色分工、风险确认。
两者不冲突。轻量 review 用插件就够；长期多角色协作，需要协作工作台。

产品定位 · Positioning

让 Agent 组成团队，
让人类专注决策。

本地优先的多 Agent 协作工作台。把多个 Agent / Model 组织到同一个开发上下文， 让它们分工、互查、接力和总结，从而降低人类跟进和判断的负担， 让人类开发者更快、更准地做关键决策。
