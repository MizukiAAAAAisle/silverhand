Silverhand IM 架构讲解

Silverhand 把多个「编码 agent CLI」(claude / codex / cursor)编排成 聊天式对话里的平等参与者——人和 agent 走同一套消息、同一套投递、同一套渲染。 这份文档自顶向下带你走一遍：它到底是什么 → 数据长什么样 → 跑在哪 → 一条消息怎么流动 → 凭什么保证不丢不重 → 读侧怎么投影 → 谁能做什么。读完你应该能在脑子里画出整张图。

0一句话看懂

先建立最粗的骨架，后面每一节都是往这根骨架上挂细节。

一个后端(control plane)拥有全部真相——领域模型、持久化、权限、路由； 一个 daemon(execution plane)拥有全部进程——spawn agent、喂 stdin、管 run-state。 两者之间只有一个抽象接口 AgentRuntimeHost。

消息写进一张 messages 表(人和 agent 用同样的列),然后分两条腿投递: 一条腿把消息塞进 agent 的 inbox(唤醒它去干活),另一条腿通过 event WebSocket 广播给所有正在看的客户端(renderer 实时渲染)。

整套系统的难点不在功能,在正确性:断线重连后不能丢帧、不能重复计数。 这靠三样东西守住——客户端权威的游标 + 三态水位(received/applied/satisfied,floor 只信 satisfied)+ 三个互不转换的序号空间。 这三样是本文档的核心,其余都是它们的应用。

读法建议 §01–03 是「静态结构」,建议顺读;§04「一条消息的一生」是枢纽,把所有静态件串成动态流; §05–06 是正确性内核,最烧脑但最值;§07–09 是挂在骨架上的子系统,可按需跳读;§10 是随时回查的速查表。

1核心不变量：人 / Agent 同构

这是整个系统的「宪法第一条」。理解了它,后面很多设计就是必然推论。

Silverhand 最根本的判断:人和 agent 是同一类参与者,只是行为策略不同。 这不是口号,而是落在数据与代码结构上的硬约束:

数据层:两列模式

参与者永远用 *_kind + *_id 两列表达,绝不用 user_id/agent_id 一对可空列硬凑:

列人Agent
from_kind'user''agent'
from_user_id有值NULL
from_agent_idNULL有值

系统消息是第三种 from_kind='system'(onboarding、状态广播)。

代码层:一个方法 + Principal

同一操作只有一个 service 方法,入参是 Principal 联合类型,在路由边界构造:

  • 没有 sendUserMessage / sendAgentMessage 两份
  • 行为差异只走 POLICIES[principal.kind] 策略表(如 requireSenderMembership、ccMentions、autoStartIdleRecipients)
  • service 内绝不出现 if (kind === 'user') 散落分支
✦ 不变量 「人和 agent 走同一 service 方法,行为差异只经 POLICIES 表、不经散落的 kind 分支。」 违反它 = 把「agent 是二等参与者」编码进控制面,未来的远程/沙箱多参与者拓扑会寸步难行。 这条由 docs/architecture-principles.md 的 review checklist 强制守护。

2领域模型：Channel-like 聚合 + reply-cluster

Workspace → Channel/DM → reply-cluster。运行流只有 channel / dm_channel 两种;thread 不是一等 conversation,而是消息层的回复群。

层级到底怎么分

  • Workspace(kind='workspace'|'dm')= 成员 agent 的容器
  • Conversation(运行流) = channel 或 dm_channel——同一 top-level 聚合的两个变体
  • Reply-cluster = 消息层概念(messages.thread_root_id),不是 conversation 的一种 kind
  • 历史 channels / sessions 表已废弃并入 conversations;旧 conversations.kind='thread' 是只读 legacy fossil,不是当前模型的一层。

Thread = reply-cluster(关键澄清)

当前模型里,thread 不是独立会话/session,而是 channel 内某条消息下由 messages.thread_root_id 聚起来的回复群:

  • 共享父 channel 的上下文与权限(follower ⊆ member)
  • 要真正隔离/并行 → 开新 channel,而不是开 thread

消息这张表上有什么

列含义
seq父 conversation 内单调序号 = MessageSeq(见 §06),持久化、重启不丢;主线与其 reply-cluster 共享同一父 conversation 的 MessageSeq 空间
from_kind / from_user_id / from_agent_id参与者两列模式(§01)
thread_root_id非 NULL = 这是某 thread 的回复;NULL = 主线消息

task_number / task_status / task_title / task_assignee任务就挂在消息行上——一条消息可被提升为 task,chip 随该 message row 渲染(见 §07 的投影 seam)
✦ DM 的特例(勿混) kind='dm' 的 workspace 恰好 1 个 agent、自动 provision、永不支持 member-add、 用 # 图标区分、不做 per-user-hide。查询侧铁律:regular 与 DM 两个 collection 各读各、绝不混 (唯一例外是全局 archived 恢复索引)。

3部署拓扑与 Daemon

同一份 backend 库,两种部署形态;backend 永不直接 spawn agent。

记住一句话:backend = 控制面(control plane),daemon = 执行面(execution plane)。 backend 管 IM 语义/持久化/权限/路由;daemon 管进程 spawn / stdin 投递 / run-state。 两者之间只隔着一个接口 AgentRuntimeHost——正因为有这层抽象,才能同一套 backend 跑出两种部署。

为什么 backend 不自己 spawn

把控制面(HTTP/DB/ACL/路由)和执行面(进程/stdin-stdout/文件系统)彻底分开。 未来云端 backend 根本够不到用户机器上的 claude 二进制和工作目录—— 只有 daemon 在用户侧才能 spawn。这层分离是可部署性的地基。

Daemon 怎么拉起一个 agent

  • 每个 (conversation, agent) 一个 CLI 进程
  • stdin/stdout 走 stream-json(NDJSON)
  • 注入 SILVERHAND_* env(conversation/agent id + token)
  • PATH 前置每次 spawn 的 bin/silverhand shim
  • per-handle drainChain 串行化 inbox drain,防止一行写两次
⚠ 硬得来的坑:Claude 的 init watchdog claude --input-format stream-json 会确定性地压住 system.init,直到收到第一条真实 stdin 消息。 所以空 inbox spawn 时,daemon 标记 active 但不立刻装 watchdog;真实消息落地、stdin 首写后才 arm。 永远不要用合成 user 消息去「预热」stdin——每条都会触发一次计费 turn 并写进 resume jsonl。

4一条消息的一生 — 枢纽

把前面所有静态件串成一次动态流动。这一节看懂,全局就活了。

当 @Alice 发一条消息,它会分两条腿走:一条腿去唤醒收信的 agent(inbox 投递梯度), 另一条腿去更新所有正在看的屏幕(event-WS 广播 → renderer 投影)。下面这张时序图是整个系统的心脏。

腿 A · inbox 投递三档(唤醒 agent)

目标是把消息送进收信 agent 的「脑子」,push 为主、pull 兜底:

  1. A 完整推:agent 在跑且处于安全边界 → 直接写 stdin 一条 user 消息
  2. B 提示推:A 失败 → 发一行 ASCII「你有 N 条待读」
  3. C 延迟:agent 没跑 → 消息留在 inbox,下次 spawn 时通过 startup_delivery 注入

Claude 这类「门控」runtime 会等到工具调用之间的安全边界才推;codex 这类「直推」立即推。

腿 B · WS 广播(更新屏幕)

目标是让所有正在看的客户端实时看到新消息:

  1. backend 往该消息 scope 广播 EventFrame{seq,epoch,kind,payload}
  2. ws-client(传输层)按 TransportSeq 连续接收 → conversation-ingestor(业务层)摄取
  3. 连续性检查(seq === last+1)→ 写进 React Query cache(投影)
  4. view 作为纯 reader 读 cache → 渲染
  5. 帧 satisfied(含没人看的 vacuous)后 markSatisfied → 推进 resume floor
为什么要分两条腿 因为「让 agent 干活」和「让人看到」是两个完全不同的消费者:agent 需要被 spawn/唤醒并注入 stdin; 人只需要屏幕刷新。它们的正确性模型也不同——腿 A 关心「不漏唤醒、不重复计费」,腿 B 关心「不丢帧、不重复计数」。 §05 专讲腿 B 的正确性内核。

5传输与游标：正确性骨架

断线重连不丢不重,全靠这一节的四个概念。系统最烧脑但最值钱的部分。

先看清三者怎么连(下图),再讲正确性。real-time 的难点从来不是「推一条」,而是「断线重连后,怎么保证既不丢帧、又不重复」——Silverhand 靠客户端权威游标 + 三态水位 + 单例 ingestor + 幂等重放守住它。

① 三者链路:客户端 / backend / daemon(先看清谁在屏幕路径上)

② 客户端权威的游标

每个 scope,客户端持有 positions[scope] = { epoch, lastSeq },整个 session 保留。 它代表「客户端已连续收到并达到 resume-safe(satisfied)的最高 seq」(即 resume floor,不是「已写进屏幕投影」)。重连时客户端拿着它发 resume{lastSeq}, 服务端从缓冲区(每 scope 200 帧)重放它之后的所有帧。

✦ 不变量:server 永不静默推过一条未见帧 subscribed ack 不得把已保留的同-epoch 游标推到 head——否则会跳过 resume 的重放(这就是 #1251 的 clobber bug)。 游标是客户端权威,ack 只是「最后兜底的基线」。

③ 三态:received · applied · satisfied(floor 推的是 satisfied,不是 applied)

从「收到一帧」到「可以安全当它处理完、重连不用再发」之间有三个状态,别压成两态——这正是「received 和 applied 到底差在哪」的答案:

⚠ 术语澄清:resume floor ≠ seam 的「applied」(曾撞名,已 rename 消除) ws-client 里 resume floor 那条水位代码名 resumeFloorPositions(#task:1281 从旧名 appliedPositions 改来、消掉撞名;注释原话「The ONLY thing resume replays from」),它 +1 的判据是 markSatisfied(satisfied)。 而 seam patchMessageInActiveProjections 返回的 applied 布尔,只表示「有没有写进一个正在显示的投影」——它是 satisfied 的输入之一,不等于 floor。 两者本是不同物:floor 那条本质是 satisfied-water / resume floor,曾因历史命名叫 applied 而混淆,现已 rename 为 resumeFloorPositions,概念与命名对齐。
状态谁写 / 何时作用
receivedws-client acceptEventFrame,每收到一个 desired-scope 帧连续性 / 找 forward-gap;不可用来恢复
appliedseam 返回的布尔,写进一个正在显示的投影时 = truesatisfied 的证据之一;本身不是 floor
satisfiedingestor markSatisfied(scope,seq,epoch);message 流经 Promise.allSettled 全 fulfilled 后一次(含 vacuous)唯一的 resume floor(重连从这往后重放);refetch 失败则钉住

对 message 流,satisfied 由汇合裁决:内容写入 ∪ 已提交的 derived-invalidate ∪ warm-remove ∪ cold-absent vacuous,全算。received 与 satisfied 会「看似同步」,直到出现只收到帧但没写任何 warm 内容的情况——这时靠 vacuous 让 floor 继续走,正是特性不是 bug。

脚注:#1263 hybrid 窄特例(别上升成通用模型) reaction / task_changed 是幂等集合写,故意用同步 applied 布尔直接当 settle 信号(真 patch → satisfied 一次,no-op → 不推进),不走 allSettled join。代码里标了这是 possible fast-follow 的窄简化——腿 B 的主模型永远是 received → satisfied → resume floor。

④ 中央 ingestor:两层(传输层 vs 业务层)

「唯一入口」要拆成两层看,否则会误记成「整个 app 一个函数收所有 WS 帧」:

  • 传输层 ws-client(EventWsClient):客户端唯一的原始 WS 帧接收/传输层——管 TransportSeq/Epoch、重连、snapshot_required、received-water,并存放 resume floor(resumeFloorPositions)
  • 业务层 conversation-ingestor:conversation/message event 的唯一业务 ingestor——把帧变成本地投影写入,且是唯一 content-driven 的 markSatisfied 调用者(它决定 floor 何时前进)
  • view 变纯 reader:useChannelMessages 等丢掉 onFrame,只是 useInfiniteQuery 读者;mount=开始读、unmount=停止读,不再门控游标

历史 bug:5–8 个 hook 各自 onWsFrame、各写各的 cache、却共用一个游标 →「组件 mount/unmount 竟决定帧是否被摄取、能否推进游标」。两层单例把「传输接收」和「内容摄取」分开后,floor 由业务层 satisfied 驱动,与订阅/挂载无关。

✦ 不变量 mount / unmount 只决定「当前有没有可写的显示投影」(即影响 applied);它不决定 received 传输连续性、不决定帧是否被 satisfied(resume floor),也绝不让 view 自己消费 WS / 门控游标。floor 前进是因为 satisfied 发生,与组件是否挂着无关。

⑤ 派生值:铁律是「权威 + replay-safe」,重取只是当前落法

铁律(replay 决定,永不变): resume 是 at-least-once,同一帧会被重放多次;所以派生聚合值(reply-count / followers / threads-list)禁止本地 +1(非幂等 delta,重放双算),必须走权威 + 幂等 + settle 后才推 floor。

当前落法: 对这些 per-viewer / 列表形、客户端无源数据的值,用 invalidateQueries → 权威重取真值(复用冷启动读模型 → live ≡ 重放 ≡ 冷开)。代价 = 一次往返 +「改一条 reply → 整窗 refetch」放大。

未来落法(S1 投影级恢复): 让 frame/recovery 带最小权威增量或投影补丁,客户端幂等 set/merge、per-projection 重放,免整窗 refetch——同样满足铁律。所以概念记成 authoritative settle,「整窗重取」只是它当下的实现,别把过渡当终局(否则文档会把 S1 升级路径写死)。

另一半判据: reaction / task_changed 是集合绝对值写(set 而非 +1)、message body 是 id-keyed append → 都天然幂等 → 可走同步 boolean 门控,不必等 refetch。判据永远是「效果是否累积重放依赖的持久状态」,不是「它是否调用 invalidate」。

⚠ 别混:InterestRegistry(#1260)是带宽,不是正确性 订阅拓扑(谁订了哪个 scope)只管「别往不关心的客户端扇帧」= 带宽优化。 正确性(apply floor / resume / dedup)是 ingestor 的活,和订阅状态无关。这条边界一旦混淆,就会把带宽逻辑误当正确性门。

6三序空间：seq brand

同样是「一个数字」,却有三种互不相干的含义。混用它们是 bug 之源,所以用类型墙彻底隔开。

系统里有三个各自独立的序号空间。它们都是 number,但语义完全不同——把一个当另一个用,就是 #1265 那类 bug 的根。 解法是名义品牌(nominal brand)+ 编译墙:每个空间是 number & {readonly [Brand]: true},类型不同,无跨空间转换 helper。

只有两条 number → brand 的路

  1. origin mint(源头铸造):DB 分配 MessageSeq、daemon 递增 TransportSeq、daemon 生成 TransportEpoch
  2. decode boundary(解码边界):DB row mapper、DTO 构造、API 入口 zod parse、localStorage 水合

其余地方拿到的必须已经是 branded。

为什么禁裸 as

裸 as MessageSeq 能在任何地方把一个坏值伪装成品牌类型,绕过 mint/decode 的管控。 所以有 fence 测试:as MessageSeq 只允许出现在 asReadSeq / asObservedSeq / decodeMessageSeq 的实现里。

renderer 收到的 wire 数据是「受信任的类型边界」——不跑 zod,权威 decode 在服务端 DTO 构造时完成。

✦ 不变量 三序空间永不跨空间转换。品牌墙挡住「空间混用」(Axis-A);而「缺席」这类问题(?? 0)品牌治不了, 要靠每个角色显式定义 absent 的含义(Axis-B)。

7读侧：投影 seam & Activity

同一条消息可能同时显示在好几个地方。读侧要保证它们「处处一致」,且 Activity 只是纯投影。

投影覆盖 seam(#1270):一条消息、多个屏幕位置

一条消息可能同时出现在:主线窗口、打开的 reply-cluster、thread-root 行、Activity 侧栏。 当它的 reaction 或 task chip 变化时,每个正在显示它的投影都要更新——历史 bug 就是某个投影被漏掉。

解法是单一 seam patchMessageInActiveProjections(qc, {channelId, messageId, threadRootId}, patchRow): handler 只交出一个「目标 + 幂等的行补丁」,seam 统一把它扇给每一个正在显示且真的含这条消息的投影。

✦ 不变量:SSOT = seam,事实源 = 投影层 「哪些投影含这条消息」由 React Query 的 observer 计数 + cache 内容判定(membership-gated,绝不 bootstrap 不存在的窗口), 不是 InterestRegistry(那是带宽边界)。双向 fence:删掉旧的 4 个 per-projection 导出 + body-scoped 源码扫描,保证 seam 是唯一的消息行补丁入口。

Activity / Attention:读侧 CQRS,零自有状态

Attention 是一个读侧限界上下文,纯投影——它不拥有 read/unread/claim/salience 任何状态, 每次都从既有源(stream 游标、notifications.read_at)重新派生。

  • 消除靠单一原语 observe():positional 项 → 推进 stream 游标;directed 项 → 写 notifications.read_at。没有独立的 activity.read_at 表。
  • 唯一写侧聚合 = ChannelAttentionPreference(每 channel 的 ambient 开关)。

进入 Activity 的规则(enter()):

enter(item, me) = directed OR ( ambient AND subscribed AND ambientPref(parentChannel) == on )
类型进入条件
directed(DM / @我 / agent 启动失败)无条件进,压过一切
channel 主线 ambientchannel 的 ambientPref == 'all'
followed-thread ambientfollowed AND 父 channel ambientPref == 'all'(aggregate-floor #1268)
⚠ delivery ⊥ attention(#1268 的核心) follow 是投递的预置条件(necessary-not-sufficient),不是 attention 决定。 所以一个 channel 设成「仅提及」时,你 follow 的 thread 里的普通回复不该冒进 Activity—— follow(投递)不能覆盖你显式的 attention 选择。attention 可以读 thread_followers 当订阅谓词,但绝不写投递状态。

8授权两轴

人按角色,agent 按能力桶。两轴正交,永不塌成一轴。

人 role-based

三种 workspace 角色 owner / admin / member,管治理操作:

  • owner:存亡级(archive/delete workspace、改人角色、授 admin)
  • admin:日常治理(建/删 channel、管 agent、加人、改设置)
  • member:读/发(受 conversation 成员资格约束)

角色 ≠ 成员资格:角色决定治理,conversation 成员资格决定「能不能看/发某条流」,两道门独立。

Agent capability-based

约 11 个能力桶(不是几十个原子操作),per-(workspace, agent) 授予:

read_messages send_messages read_tasks create_tasks write_tasks read_attachments upload_attachments create_channels manage_conversation_members manage_schedules

缺能力 → 路由返回结构化 capability_denied(不可重试);agent principal 是 (conversationId, agentId),能力查 workspace_agent_capabilities。

✦ 不变量:两轴正交 改一轴不影响另一轴。workspace owner(可能是人)能治理 workspace 但改不了某 agent 的 profile; agent 的创建者(普通 member)能编辑该 agent 但 archive 不了 workspace。这条防的是「任何成员都能删 workspace」那种洞。

9在线状态(Presence)

不是新子系统,是一个「连接存在性」的投影。

人 online ⟺ 至少有 1 条活的 event-WebSocket 连接(/api/ws/events)。 没有心跳、没有新轮询器——纯粹是连接存在性的投影。

  • 内存里 PresenceRegistry = Map<userId, Set<connId>>:0→1 转 online,1→0 起宽限计时(~20s)后转 offline
  • 二态 online | offline(v1 无 away/idle)+ users.last_seen_at
  • last_seen_at 记的是断开那一刻,不是计时器到期时刻
  • 广播走全局 app scope(v1 不按 workspace 过滤)

与「host 可用性从 HostWsAttachment 存在性派生」同构——都是「连接在不在」的投影。
